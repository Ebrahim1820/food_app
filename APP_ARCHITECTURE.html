Introduction

This one Flutter codebase renders two completely separate apps that happen to share infrastructure (login, push notifications, real-time updates, caching, translations):

  • 🛍️ Customer app — browse food offers, place orders, track them, manage favorites/profile/addresses.
  • 🏪 Business app — manage a restaurant/shop's offers, handle incoming orders in real time, manage the team and bank account.

After login, AuthGate reads the user's role from the JWT and routes them into exactly one of these two experiences (there's also a third, smaller Admin dashboard, out of scope for this document). A single account can also switch between the two if it has both a customer identity and business access — both the customer drawer and the business drawer have a "switch view" shortcut.

📌 How to use this document Jump to the section for whatever you're touching. Each feature section covers, in order: the Screens (what the user sees), the Controller (the state + logic behind it), the Service (the actual network calls), and any notable widgets. Customer and Business sections are entirely separate — nothing is mixed together.

Architecture Pattern (GetX)

Every feature in this app follows the same four-layer flow. Once you've understood it once, you've understood the whole codebase:

Screen lib/screens/** Pure UI. Reads reactive .obs values wrapped in Obx(() => ...) so it rebuilds automatically. Contains zero business logic or network calls.
Controller lib/controllers/** A GetxController. Holds state as .obs fields, exposes methods the screen calls (e.g. fetchOrders()), talks to one or more Services.

Dependency wiring — InitialBinding

lib/bindings/initial_binding.dart is where every Service and Controller is constructed and registered, once, at app startup. Two registration styles are used throughout the app:

Style Meaning Used for
Get.put(x, permanent: true) Created immediately, lives for the app's entire lifetime ApiService, KeycloakAuthService, PushNotificationService, NotificationController, LocationController, BankAccountController

On logout, InitialBinding.clearUserControllers() force-deletes every user-scoped controller so the next login starts with a clean slate instead of showing the previous user's stale data.

Authentication

Login/registration screens differ per audience (covered in each app's own section), but the underlying token machinery is one shared system.

Service KeycloakAuthService lib/screens/auth/keycloak_auth_service.dart

Registered permanent: true. Talks directly to Keycloak (not the Symfony API) using its own bare Dio instance with no auth interceptor — attaching an interceptor here would create an infinite refresh loop.

Method What it does
login(username, password) Direct Access Grant — POST {keycloakBaseUrl}/realms/{realm}/protocol/openid-connect/token. Throws incorrect_credentials or server_unreachable.
getValidAccessToken() Decodes the stored JWT's exp; if it expires within 30s, silently refreshes first. Uses a Completer mutex so concurrent callers share one in-flight refresh instead of firing N parallel refresh requests.
forceRefreshToken() Discards the cached token and refreshes unconditionally — used after the server itself rejects a client-side-still-valid token (401).
logout({localOnly}) Best-effort POST .../logout + clears secure storage.
getRolesFromToken(token) Decodes realm_access.roles from the JWT payload — this is how the app knows if someone is ROLE_USER, ROLE_BUSINESS_PARTNER, ROLE_MEMBER, or ROLE_ADMIN.
homeRouteForRoles(roles) Role → route mapping, used by both AuthGate and LoginController to send the user to the right dashboard.

App-wide singleton (permanent: true), also a WidgetsBindingObserver so it can react to app foreground/background transitions.

Networking & Automatic Token Refresh

Service ApiService lib/network/api_service.dart

The single Dio instance the whole app's business logic talks through — every other Service (FoodOfferService, OrderService, etc.) is constructed with this one shared instance, so configuring auth here means every request everywhere is authenticated automatically. Two interceptors are attached in the constructor:

  1. An inline InterceptorsWrapper that rewrites options.baseUrl = ApiConstants.baseUrl on every request — because the Dio instance is constructed at app startup, before the dev-host probe (see below) has resolved which IP to use. Without this, requests would freeze onto whichever host happened to be first when the app launched.
  2. AuthInterceptor — see below.
Interceptor AuthInterceptor lib/screens/auth/auth_interceptor.dart

Runs on every request/response through the shared Dio client. Screens never touch tokens directly — they just call a Service method and this interceptor handles the rest.

onRequest

Skips token injection entirely for requests tagged Options(extra: {'noAuth': true}) (public endpoints like browsing offers). Otherwise calls getValidAccessToken() and attaches Authorization: Bearer <token>. If there's genuinely no token left, rejects the request immediately with a session_expired marker (distinguished from a transient network failure during refresh, which fails normally instead of forcing a logout).

onError

Condition Behavior
session_expired marker from onRequest Redirects to Login (Get.offAllNamed), guarded by a _redirecting flag so multiple concurrent 401s don't stack duplicate navigations.
HTTP 403, not tagged silent403 Shows a global "permission denied" snackbar with the backend's error message — a safety net so screens without bespoke 403 handling still tell the user something. Bulk lookups that are expected to sometimes 403 (e.g. fetching N team members' profiles) tag their requests silent403: true so one failure doesn't spam N stacked snackbars.
HTTP 401, first occurrence Calls forceRefreshToken() (not the cached token — that's exactly what just got rejected), retries the original request once with the new token (tagged _retried to prevent infinite loops). If refresh itself fails, logs out and redirects to Login.
Retry with a fresh token still fails Treated as a real permissions problem, not a session problem — does not force logout, lets the calling screen show its own error state.

Dev-host resolution (why the app finds your laptop automatically)

lib/constants/api_constants.dart — ApiConstants.resolveDevHost(). On development builds, the backend runs on a laptop whose IP changes per network (home Wi-Fi, hotspot, emulator, simulator). This probes a priority list of known hosts (10.0.2.2 for Android emulator, localhost for iOS simulator, then known LAN/hotspot IPs) by opening a TCP socket to each in parallel, and uses the first one that responds. Runs from AuthGate, in parallel with the auth check and the splash animation, so it never adds extra wait time.

Real-Time Updates (Mercure)

A faster, complementary channel alongside FCM — Server-Sent Events (SSE) pushed from a Mercure hub, used where near-instant UI refresh matters more than FCM's delivery latency allows. Six topics total: three public (no auth), three private (JWT-gated).

Controller MercureController lib/controllers/mercure_controller.dart

Single source of truth for the session's Mercure subscriber credential — permanent: true, shared by both apps. Calls GET /me/mercure-token once per session (ensureLoaded(), called from LoginController.signIn() and AuthGate's app-restore path, right next to the existing /users/me calls) and exposes tokenRx (reactive JWT) plus topicsRx (the private topics this user is authorized for). Every user gets users/{id}/orders; a business-linked user (owner or staff) additionally gets business-partners/{id}/orders and business-partners/{id}/reviews — exposed as the userOrdersTopic/businessOrdersTopic/businessReviewsTopic getters rather than callers hardcoding a topic string.

Proactively refreshes by decoding the JWT's exp claim and re-fetching ~30 seconds before it expires (falls back to a fixed 30-minute interval if the token has no readable exp). Subscribers don't run their own refresh timers — they ever(mercureCtrl.tokenRx, ...) and simply resubscribe whenever the token changes. clear() is called from InitialBinding.clearUserControllers() on logout so the next login fetches a token scoped to whoever just logged in.

⚠️ Breaking change from the old per-business endpoint Replaces GET /business-partners/me/mercure-token → {token, topic} (singular, business-only). The new GET /me/mercure-token → {token, topics: [...]} is called for every logged-in user, not just business partners.

Each topic decodes into a small event model (MercureOfferEvent, OfferStockMercureEvent, BusinessStatusMercureEvent, UserOrderMercureEvent, OrderMercureEvent) — a subset of the full model, just enough to know "something changed" (or, for the two public offer-detail topics, enough to patch the open screen directly without a refetch).

City slug has no backend field "Current city" for food-offers/city/{citySlug} is a Flutter-side decision — this app derives it from AddressController.selectedAddress.city, slugified by MercureService.citySlug() (lowercase, accents stripped, punctuation → hyphens). A customer with no selected address gets no live new-offer alerts until they pick one.
⚠️ The SSE client never surfaces HTTP status codes The flutter_client_sse package used here does not expose the connection's HTTP status to callers — a 401 (expired/invalid token) looks identical to a normal idle reconnect (silent internal retry). This is why token refresh for private topics is proactive (via MercureController's JWT-exp timer) rather than reactive. The package also prints its own raw ---ERROR--- / ---RETRY CONNECTION--- / --SUBSCRIBING TO SSE--- lines straight to the console on every drop-and-reconnect — cosmetic noise from a healthy connection recovering, not a Dart exception and not necessarily a sign of a real problem, unless it loops continuously or live events genuinely stop arriving afterward.
⚠️ Solved 2026-07-19 — private topics are full IRIs, not bare paths MercureController's topic matcher originally compared with t.startsWith('users/') / t.startsWith('business-partners/'), assuming the backend would send bare paths like users/1/orders. Real device logs showed the backend actually sends full IRIs: https://api.template.local/users/1/orders. That never starts with users/, so userOrdersTopic/businessOrdersTopic/businessReviewsTopic always returned null, and every private-topic subscription silently never connected at all — not "connects but receives nothing" (that would be the missing-Authorization-header failure mode), the SSE call was never even made. Fixed by MercureController._topicPath(), which strips a scheme://host/ prefix (if present) before the prefix/suffix comparison, so the matcher works for both shapes. Still returns the original untouched string as the actual subscribed topic: — only the comparison operates on the stripped path.
Reliability Order status live-refresh & stock-restore-on-cancel

Two related but separate real-time behaviors, both debugged end-to-end on 2026-07-19 via a live user report ("status shows Pending", then "quantity not updated") plus device logs — kept together here since the fixes build on each other chronologically.

1. Order status not reflecting on the open detail screen

OrderController.refreshAfterOrderChange() (used by both the users/{id}/orders Mercure handler and the order_status_changed FCM path) refreshes the flat orders list and, if selectedOrder is currently set, re-fetches that specific order via fetchOrderById. Before this fix, a list-only refresh left OrderDetailScreen (which reads the separate selectedOrder field) stale even though the event genuinely arrived — the exact same class of bug independently found and fixed in BusinessOrderController.updateStatus() (which already correctly re-fetched selectedOrder when open) and in the two offer-detail screens' Mercure conversion below.

2. Quantity not restoring on cancel — the real chain of bugs

Four call sites credit stock back after a cancellation: OrderController.cancelOrder() and .deleteOrder() (customer-initiated), BusinessOrderController.updateStatus() transitioning to 'cancelled' (business-initiated), and OrderController.refreshAfterOrderChange() (customer's view of a business-initiated cancellation, via a before/after status-snapshot diff). Getting this reliable took four separate fixes:

Bug Fix
Weight-based offers never restored weightAvailableKg — FoodOfferController.restoreQuantities() unconditionally bumped quantityAvailable for every matched offer, which also corrupted weight-based offers (meant to keep that field null) with a bogus non-null value Branch on isWeightBased: weight-based offers restore weightAvailableKg via OrderItemModel.weightTotalKg; everything else restores quantityAvailable as before
BusinessOrderController.updateStatus() had zero restore logic — a partner cancelling/rejecting their own order never saw their own Menu tab's stock go back up Added BusinessOfferController.restoreQuantities() (same weight-based branch, writes into the flat myOffers list), called from updateStatus() guarded against double-crediting a retry
refreshAfterOrderChange() only refreshed order data — a business-initiated cancellation never restored the customer's stock view Snapshot each order's status before fetchOrders() replaces the list, diff after, restore for any order that just transitioned to 'cancelled' (guarded against misreading the very first fetch as a mass transition)
The actual remaining blocker, found via device log (restoreQuantities: crediting 1 item(s) for offer id(s) [0]) — the orders list endpoint (GET /orders?businessPartner=… / ?user=…) serializes orderItems[].foodOffer as null. OrderItemModel.fromJson falls back to FoodOfferModel.fromIri(''), which can't parse an id out of an empty string and defaults to id: 0 — an id that can never match a real offer, so every restore call above silently credited nothing despite running correctly in every other respect Added _itemsForRestore(order) to both order controllers: if any item's foodOffer.id looks like the null-fallback (0), fetches the full order via getOrderById() — which does reliably embed a real foodOffer — and restores using those items instead. All four call sites now await this before restoring.
Why placing an order was never affected by the id-0 bug The stock-decrement path (OrderController._reduceOfferQuantities, called from placeOrder()) builds offer ids from the customer's own locally-known checkout selection, never from a backend-echoed OrderItemModel — so it was never exposed to the list endpoint's foodOffer: null serialization gap in the first place. Only the restore path, which has no choice but to read the offer id back off an already-placed order, hit it.

Caching

Three independent caching layers, each with a different job.

🔄 2026-07-19 — migrated the key/value layer from get_storage to hive_ce, added a TTL Two gaps existed before this change: (1) every cache entry recorded a ts timestamp but nothing ever read it back, so stale data could sit on screen indefinitely instead of only briefly; (2) get_storage is a flat JSON-file key/value store with no querying and no real scaling story for larger data sets. Fixed both — see the AppStorage card and TTL note below — and used the same change to extend caching to screens that had none before (Favorites, Business Menu, Business Orders, Admin Dashboard).
Service AppStorage lib/services/app_storage.dart

Thin wrapper around a single Hive box (hive_ce + hive_ce_flutter), deliberately shaped like get_storage's API — read<T>(key) / write(key, value) / remove(key) / hasData(key) / getKeys() — so every one of the six previous GetStorage() call sites (locale, avatar URLs, the offer/order/partner data cache, the default-bank-account id, the FCM push-token id) only needed its constructor swapped, not its call shape. Opened once in main() via AppStorage.init(), in parallel with Firebase.initializeApp().

Why Hive instead of GetStorage, Isar, or Drift/SQLite?
  • vs. GetStorage — GetStorage writes one JSON file to disk and re-parses the whole thing on every read; fine for a handful of small blobs, but it doesn't scale and offers no querying. Hive is a proper embedded key/value database (binary format, per-key reads) with a near-identical API, so the swap was low-risk.
  • vs. Isar — Isar gives real indexed queries, which this app doesn't need yet (every cache lookup is "give me the blob for this one key," never "find all entries where…"). Isar's own maintainer also stepped back from the project, making a community fork the only actively-maintained option — extra risk for a feature this app isn't using.
  • vs. Drift/SQLite — Drift is the right tool for relational data with joins (e.g. querying order items across offers), but every cache entry here is a single self-contained JSON blob keyed by name. A full SQL layer would be pure overhead for that shape of data.
hive_ce — the actively-maintained community fork — was picked specifically over the original hive package, whose maintenance had also slowed.
Layer Library Purpose
API data cache hive_ce (via AppStorage) through DataCacheService Shows the last-known data immediately on launch, before the network round-trip completes, so the UI never opens blank. A yellow StaleBanner appears whenever the visible data is cached rather than fresh.
Image pixel cache cached_network_image + flutter_cache_manager Avoids re-downloading offer photos/avatars on every screen visit — disk cache, not just memory.
Avatar URL cache hive_ce (via AppStorage), keys prefixed avatar_url__ Stores the resolved CDN URL so it isn't re-fetched from the profile API on every app open.

TTL — a cache entry that's too old is treated as no cache at all

DataCacheService.load(key, parse, {maxAge = Duration(minutes: 5)}) compares the entry's saved ts against DateTime.now() before returning anything. Past maxAge it returns null, exactly as if nothing had ever been cached — the caller falls through to its normal fetch-and-spinner path instead of briefly showing minutes- or days-old data. Previously ts was written but never read back, so a cache entry from days ago could still flash on screen for a moment before the fresh fetch replaced it.

Perka launches in Iran, where international card networks (Visa/Mastercard) are unusable under sanctions — so "pay online" here always means a redirect through a domestic interbank gateway, never an in-app card-number field (that's not how any of these PSPs integrate — PAN capture stays on the bank's own page).
